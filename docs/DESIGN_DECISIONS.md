## 1. Model choice

### 1.1 The decision

Four architectures were trained on identical folds and compared under one rule.
**`baseline_cnn`, a 250 K-parameter CNN trained from scratch, was promoted.**

| model | params | test F1 | defect recall | p95 latency | throughput |
| --- | ---: | ---: | ---: | ---: | ---: |
| **`baseline_cnn`** ← promoted | 0.25 M | **0.9970** | 0.9952 | **2.79 ms** | 628 img/s |
| `resnet18` | 11.17 M | 0.9964 | 0.9941 | 19.19 ms | 114 img/s |
| `mobilenet_v3_small` | 0.93 M | 0.9929 | 0.9905 | 9.42 ms | 569 img/s |
| `logreg_hog` *(classical control)* | ~0.002 M | 0.9609 | 0.9620 | 2.91 ms | 389 img/s |

*Source: `reports/model_comparison.csv`, generated from tracked MLflow runs.
Test split n = 1,457, held out and evaluated once.*

### 1.2 Why a classical control was included

`logreg_hog` (Histogram of Oriented Gradients + logistic regression) exists so
that **"we used deep learning" is a measured decision rather than an
assumption**. HOG is the right classical baseline for this task — it is a
texture/edge descriptor and surface defects *are* local texture anomalies — so
it is a genuine attempt, not a straw man.

It reaches **0.9609 F1**. Respectable. The **~3.6-point F1 gap** to the CNN is
the quantitative argument for deep learning on this problem, and without
measuring it the argument would not exist.

*Why HOG loses:* it pools orientation statistics over 16 px cells, so a defect
covering a handful of pixels contributes a small perturbation to a
1,764-dimensional descriptor dominated by the impeller's blade edges. A CNN can
learn a filter that responds to the defect specifically.

Implementation: `src/defectvision/models/classical.py`.

### 1.3 Why the small CNN beat the large pretrained one

This is the result that most needs justifying, because it inverts the
expectation that transfer learning wins.

`baseline_cnn` scores 0.9970 F1 against `resnet18`'s 0.9964 — but their 95%
bootstrap confidence intervals overlap almost entirely:

| model | test F1 (95% CI) |
| --- | --- |
| `baseline_cnn` | 0.9970 [0.9942, 0.9994] |
| `resnet18` | 0.9964 [0.9934, 0.9988] |

**The test set cannot resolve a difference between them.** With 1,457 images,
a 0.0006 gap is noise. Claiming the small model is "more accurate" would be
unsupportable.

What *is* resolvable is cost: **2.79 ms vs 19.19 ms p95 latency — 6.9× faster —
and 45× fewer parameters.** So the honest reading is: on a well-separated task,
the ImageNet backbone bought nothing measurable and cost throughput.

The promotion rule encodes exactly this reasoning rather than leaving it to
judgement (`select_best()` in `src/defectvision/training/compare.py`):

1. **Gates first.** A candidate must clear absolute floors — test F1 ≥ 0.85,
   defect recall ≥ 0.85 — and a p95 latency ceiling of 250 ms, *before* it is
   eligible. A model that is merely the best of a bad field should not reach
   production by default.
2. **Then rank** by the selection metric (test F1).
3. **Then tie-break on latency** among candidates scoring inside the leader's
   bootstrap confidence interval. When accuracy is statistically
   indistinguishable, the cheaper model is the better engineering choice.

All four cleared the gates; the tie-break selected `baseline_cnn`.

### 1.4 The architectural decision that made the CNN work at all

**Average + max pooling head, not global average pooling.**

This was not a tuning preference — it was the difference between a working model
and a broken one. A defect occupies **well under 1% of the frame**. Global
average pooling divides that evidence across the entire feature map, where the
casting body swamps it.

Measured during development: with a GAP-only head the network sat at **0.50
accuracy — exact chance — for 10 epochs**, with defect recall oscillating
between 0.00 and 1.00 (the classic signature of a model that has learned only
the base rate). Concatenating global **max** pooling put the same network on a
learning trajectory that reached 0.99.

Max pooling asks the question the task actually poses: *is there a defect-like
response **anywhere**?* The average branch is retained alongside it, contributing
information about overall surface texture.

Implementation and rationale: `src/defectvision/models/baseline_cnn.py`.

### 1.5 Grayscale stem adaptation for the transfer models

ImageNet backbones expect 3 channels; casting images are grayscale. The obvious
approach — repeat the single channel three times — triples the stem's compute
for no new information.

Instead the first convolution is rebuilt with `in_channels=1` and its pretrained
weights are **summed across the RGB axis**. This is response-identical, not an
approximation: a grayscale pixel replicated to (r, g, b) produces
`w_r·v + w_g·v + w_b·v`, which is exactly `(w_r + w_g + w_b)·v`. No pretrained
signal is lost — the filters keep their learned edge and blob selectivity from
epoch zero — at a third of the stem cost.

The claim is asserted numerically in
`tests/test_models_and_training.py::test_grayscale_stem_adaptation_preserves_response`,
so a future refactor cannot silently break it.

Implementation: `src/defectvision/models/transfer.py`.

## 2. Drift-detection approach

### 2.1 The decision

Monitor **seven interpretable image statistics** computed at request time,
compared against a baseline frozen from the **training split**, using **PSI as
the primary detector**, with **KS** as corroboration and **chi-square** for
categorical signals.

Implementation: `src/defectvision/monitoring/drift.py`,
`src/defectvision/monitoring/reference.py`.

### 2.2 Why these features, and not embeddings

The monitored vector is:

| statistic | what a shift in it means physically |
| --- | --- |
| `mean_intensity` | line lighting got brighter or dimmer |
| `std_intensity` | contrast collapsed — fogged lens, diffuser change |
| `p05_intensity` / `p95_intensity` | shadows crushed / highlights blown out |
| `edge_density` | part geometry changed, or the image went soft |
| `laplacian_var` | focus drifted — the classic blur detector |
| `entropy` | information content dropped — occlusion, washout |

**Alternative considered: a CNN penultimate-layer embedding.** It would detect
drift too, and would catch shifts these scalars miss. It was rejected on three
grounds: it is expensive at request time; its dimensions have no physical
meaning; and **when it fires, nobody can say what changed.**

The evidence that this was the right trade-off is in the PSI heatmap
(`reports/figures/monitoring/psi_heatmap.png`). The **pattern** of which
features fire identifies *which fault occurred*:

| scenario | fires | stays at noise floor |
| --- | --- | --- |
| `focus_blur` | `laplacian_var` 12.43 | `mean_intensity` 0.02 |
| `lighting_dim` | `mean_intensity`, `p05`, `p95` 12.4–15.2 | — |
| `sensor_noise` | `edge_density`, `laplacian_var` 12.43 | `mean_intensity` 0.01 |

So the output is not merely *"something changed"* — the signature says **which
part of the capture rig to go and inspect.** An embedding detector would fire
just as reliably and tell the on-call engineer nothing about where to start.

A secondary benefit: the same statistics module is used by the offline pipeline
*and* the serving container (`src/defectvision/features/image_stats.py`), so
online and offline values are computed by identical code. That is a structural
defence against training–serving skew, not a convention.

### 2.3 Why PSI is the primary detector

**PSI is not a hypothesis test.** Its value does not grow with sample size —
10,000 requests will not flag a shift that 500 would have called stable. That
property is precisely what makes it safe to put a fixed threshold on.

This is asserted as a test, not assumed:
`tests/test_monitoring.py::test_psi_is_insensitive_to_sample_size` compares the
same effect measured on 400 and 8,000 samples and requires agreement.

**KS is used only as corroboration.** It is a proper test on the full empirical
CDF, so it catches shape changes PSI's binning can smooth over — but with enough
samples it rejects on differences far too small to act on. Making it a trigger
would produce alert fatigue. **Chi-square** handles the categorical signals
(predicted-class mix, decision mix) where neither of the others applies.

### 2.4 The detail that decides whether any of it works

**Bin edges are derived from the reference distribution and frozen.**

Recomputing quantile bins on each window would make every window look like a
perfect match to itself, and PSI would sit near zero regardless of what
happened. The edges are computed once in `build_reference()` and persisted to
`monitoring/reference_stats.json`.

Asserted in `tests/test_monitoring.py::test_frozen_edges_are_reused`: with
frozen edges a 2σ shift scores PSI > 0.5; with recomputed edges the *same*
shifted data scores < 0.01.

Related: the baseline is the **training** distribution, not "the first day of
production traffic". The question monitoring answers is *"does the model still
see the kind of data it learned from"*, so the baseline has to be what it
learned from. Anchoring on early production traffic would bake in whatever was
already wrong on day one.

### 2.5 Why a `baseline` control scenario exists

The drift sweep always runs an uncorrupted control first. It measures **0.051
PSI with 0 drifted features** — below the 0.10 warn band.

That number is what makes every other row readable. Without it, a PSI of 7.34
means nothing; against a known noise floor of 0.05, it is unambiguous. Reporting
drift against zero rather than against the sampling-noise floor is one of the
easiest ways to produce a monitoring report that cannot be acted on.

### 2.6 Why one scenario is real, not simulated

Five scenarios are physically-motivated corruptions (lamp drift, camera remount,
defocus, sensor noise, a combined new-variant). But a monitoring stack validated
only against corruptions it was designed for is circular.

So `casting_512x512` — 1,300 images of the **same production line captured by a
different camera at a different resolution** — was deliberately **excluded from
training** and held back as the `real_camera_upgrade` scenario. It is an
authentic covariate shift that no corruption operator was tuned against.

It was detected: **PSI 7.344, 6 drifted features, 0.2166 accuracy drop.**
Folded into training it would have been 1,300 rows of near-duplicate parts; held
back it is the only honest test of whether the monitoring works.

### 2.7 The evidence: what the approach actually caught

*Source: `reports/drift_report.md`, current run.*

| scenario | max PSI | accuracy | acc. drop | mean confidence |
| --- | ---: | ---: | ---: | ---: |
| `baseline` *(control)* | 0.051 | 0.9950 | +0.0016 | 0.989 |
| `focus_blur` | 12.434 | 0.9925 | +0.0041 | 0.959 |
| `camera_angle` | 12.434 | 0.9400 | +0.0566 | 0.963 |
| `new_variant` | 12.617 | 0.8375 | +0.1591 | 0.927 |
| **`real_camera_upgrade`** *(real)* | 7.344 | 0.7800 | +0.2166 | 0.972 |
| `sensor_noise` | 12.434 | 0.7425 | +0.2541 | 0.910 |
| `lighting_bright` | 12.617 | 0.6100 | +0.3866 | 0.970 |
| `lighting_dim` | 15.185 | 0.5775 | +0.4191 | **0.996** |

**The `lighting_dim` row is the justification for this entire approach.**
Accuracy collapses from 0.995 to 0.578 — the model is wrong on 42% of parts —
while its mean confidence *rises* to **0.996**. It is confidently,
catastrophically wrong. This is a textbook **silent failure** (M1/CS1).

Counting alerts across the seven degraded scenarios:

- **Confidence-based monitoring alone: 1 of 7 caught** (only `sensor_noise`
  fired `confidence_collapse`).
- **PSI against the frozen training baseline: 7 of 7 caught.**

A system that monitored only the model's own certainty would have missed six
degradations including the worst two. That asymmetry is the whole argument for
monitoring the input distribution.

### 2.8 On the magnitude of PSI

The conventional bands (0.10 warn / 0.25 significant) are calibrated for the
subtle shifts typical of tabular credit scoring. Double-digit values here are
not an error — PSI is unbounded, and ~12.4 is the arithmetic signature of a
distribution that has moved **entirely outside the reference support** (all mass
in one reference bin, the other nine effectively empty; the ε-floor prevents the
log term diverging).

Anything above roughly 1.0 should be read as *"a different distribution"*, not
as a multiple of the alert threshold. This directly informs §3.3.

## 3. Retraining trigger

> Full design, including the rule table and thresholds with their derivations,
> is in **[`RETRAINING_DESIGN.md`](RETRAINING_DESIGN.md)**. This section states
> the decisions and why they were taken.

### 3.1 The decision

Retraining is governed by a **policy**, not a threshold. Four rules are
evaluated per 200-prediction window, and a breach must survive **persistence**,
**cooldown** and **label-sufficiency** gates before it can fire. The outcome is a
**routed action**, of which retraining is only one option.

Implementation: `src/defectvision/monitoring/retrain_trigger.py`.

### 3.2 Why not `if psi > 0.25: retrain()`

The naive rule fails in four independent ways, each with a real cost:

| failure | cost | mechanism |
| --- | --- | --- |
| Fires on one noisy window | Retrains on a shift change or an odd batch | **Persistence** — breach must hold across 2 consecutive windows (400 parts) |
| Fires without labelled data | Retrains on old data + noise; strictly worse than nothing | **Label sufficiency** — ≥ 300 newly labelled samples |
| Fires again right after a retrain | Infinite loop, burning compute and churning production models | **Cooldown** — 24 h, persisted to disk so it survives restarts |
| Treats every signal as "retrain" | Retrains when the fix was a threshold, or a lens wipe | **Severity routing** — see §3.3 |

### 3.3 The two routing decisions that matter most

**Drift with intact accuracy → `monitor`, not `retrain`.**
If PSI is high but labelled accuracy has barely moved, the model *generalises* to
the new regime. Retraining would spend compute and introduce deployment risk to
fix a problem that does not exist. This is the most common false positive in
drift monitoring, and this rule is worth more than any threshold tuning.

**Very large drift → `investigate_capture`, not `retrain`.**
A PSI above 0.5 on *image statistics* is rarely the parts changing; it is a lamp,
a lens, or a camera pose. **Retraining on data from a broken capture rig bakes
the fault into the model** — and then a second retrain is needed once someone
repairs the camera. Inspect the hardware first.

The five possible actions: `none`, `monitor`, `recalibrate_or_retrain`,
`investigate_capture`, `retrain`. Only the last sets `should_retrain: true`
(and exit code 10, so cron or CI can branch on it).

### 3.4 The evidence: the trigger's actual decision

*Source: `reports/retraining_decision.json`, current run.*

```
should_retrain : False
action         : investigate_capture
fired rules    : ['data_drift_psi']
windows        : 18
labels avail   : 3176
reason         : Severe input drift (PSI 6.920). A shift this large usually means
                 a hardware or configuration change (lamp, lens, camera pose)
                 rather than a genuine change in the parts. Inspect the capture
                 rig before retraining -- a model retrained on a broken camera
                 bakes the fault in.
```

Faced with drift severe enough that a naive rule would have fired immediately,
the policy **declined to retrain** and instead produced an actionable
maintenance instruction. That is the designed behaviour, demonstrated on real
data rather than asserted.

### 3.5 Human in the loop

Two mechanisms, both required by M5 / CS10:

**Review band.** Predictions with P(defect) in [0.35, 0.65] return
`decision: "human_review"` instead of an auto-action. A probability just past the
threshold is a coin-flip dressed as a decision. The review *rate* is itself a
monitored signal, because the review queue is staffed and its overflowing is a
business problem regardless of accuracy.

**Feedback endpoint.** `POST /feedback` attaches ground truth to a past
prediction by `request_id`. This models the real timing — labels arrive from
teardown, rework or customer returns, hours or days after the prediction — and
the schema treats delayed labels as normal rather than as an afterthought.
Without it, Tier-3 accuracy signals would never exist.

## 4. Problem framing and metric choice

### 4.1 The defect class is the positive class

The two errors have very different costs. A false alarm sends a good part to
manual review (cheap); a missed defect ships (expensive, possibly a recall).
"Positive" therefore means *the thing we must not miss*, and **defect recall is
the headline metric**. Accuracy is reported only for completeness.

The promotion gates reflect this: defect recall is a **separate gate** from F1,
so a model cannot compensate for poor recall with good precision.

### 4.2 A single logit, not a two-way softmax

Every deep model emits one logit per image. `sigmoid(logit)` is directly
P(defect) — which is what the operating threshold is tuned against, what gets
logged for monitoring, and what the review band is defined over. It also lets
class imbalance be handled with a scalar `pos_weight` rather than a weight
vector.

### 4.3 The threshold is tuned, and tuned on validation

**0.5 is where a sigmoid happens to cross, not where the business optimum sits.**
The operating point is selected on the **validation** split by maximising F1 over
501 candidates, then **frozen** and applied once to test. The promoted model's
threshold is **0.16**, not 0.5.

Tuning on test would leak the test set into the model's configuration and
inflate the reported score. The sequencing is: select the epoch on validation →
tune the threshold on validation → touch test exactly once.

A `target_recall` strategy is also implemented, for when a missed defect carries
a contractual or safety penalty: recall becomes a *constraint* and precision is
maximised subject to it.

### 4.4 Confidence intervals accompany every headline metric

With 1,457 test images, an F1 of 0.9970 and one of 0.9964 may be
indistinguishable. Reporting point estimates alone would invite an unsupportable
claim. Percentile bootstrap CIs (500 resamples) are computed for F1, recall,
precision and accuracy — and, as §1.3 shows, they changed the promotion outcome.

Implementation: `src/defectvision/training/evaluate.py`.

## 5. Data pipeline decisions

### 5.1 Validation severity is split, deliberately

Per-file problems **quarantine** the file; corpus-level problems **abort** the
run. A production line always produces a few bad frames, so making every check
fatal trains people to disable validation — while making none fatal means nobody
reads the report.

### 5.2 Two hash types, because they answer different questions

- **SHA-256 of file bytes** → *exact* duplicates. **Dropped** (64 found).
- **dHash (perceptual)** → *near* duplicates, surviving re-encoding.
  **Grouped, not dropped** (412 found).

Near-duplicates are legitimate data — industrial datasets photograph the same
part repeatedly. But if copies straddle the train/test boundary, the test score
measures memorisation. This is the single most common reason an image classifier
scores 0.99 offline and disappoints in production.

The splitter therefore assigns **whole groups** to folds and asserts the
invariant, raising if it is ever violated:
`Leakage check passed: 6872 groups, none spanning folds`.

### 5.3 A shortcut-leakage check runs before any training

Cohen's *d* is computed for every global image statistic between the classes,
warning if any single one nearly separates them (*d* > 2.0).

If brightness alone separated `ok` from `defect`, a "defect classifier" could be
a threshold on brightness — scoring beautifully offline and collapsing the first
time someone changed a lamp. The real corpus passes: no statistic comes close.
Catching this class of dataset artifact *before* an afternoon of training is
cheap insurance.

### 5.4 The dataset version is a file, not a runtime operation

`data/processed/manifest.csv` pins which image is in which fold. Producing a
*file* rather than splitting on the fly makes the dataset a reviewable, hashable,
DVC-tracked object — so *"which images did run #7 train on"* has an exact answer
months later. Its SHA-256 is logged to every MLflow run and embedded in the
deployed model bundle.

### 5.5 Random erasing is disabled

`random_erasing_p: 0.0`, on purpose. A defect here can occupy fewer than 100 px;
erasing a random patch can delete the only evidence while the label still reads
"defect". That is **label noise dressed up as regularisation**.

The augmentation policy that *is* used mirrors the nuisance factors a real
inspection cell produces — placement jitter, lamp drift, focus wander, sensor
noise — so it doubles as pre-emptive hardening against the M5 drift scenarios.
Corruptions the camera cannot produce (colour shifts, perspective warps) are
deliberately absent.

## 6. Packaging and serving decisions

### 6.1 Preprocessing ships inside the model bundle

The most common way an image service silently degrades is that it resizes or
normalises slightly differently from training.

The bundle carries weights **+ the preprocessing spec + class ordering + the
tuned threshold**, and the service builds its transform **from the bundle**, not
from `params.yaml`. Editing config after a model ships therefore *cannot* change
how that model sees an image. Asserted in
`tests/test_serving.py::test_preprocessing_travels_with_the_weights`.

### 6.2 The serving container has no MLflow

Experiment tracking is a development concern. Putting MLflow and a database
driver on the request path would add ~200 MB and a failure mode for no runtime
benefit. The bundle is plain `torch.save` output and loads without it.

MLflow remains in use for tracking and the Model Registry — the promoted model is
registered as `defectvision-classifier` for lineage and discovery, not for
serving.

### 6.3 Liveness and readiness are separate endpoints

A container whose model failed to load is *alive* but must not receive traffic.
Collapsing the two either restart-loops a healthy process or routes requests to a
broken one. With no model, `/healthz` returns 200 while `/readyz` returns **503**
with the reason in `detail`.

### 6.4 Every malformed input maps to a typed 4xx

A 500 in the logs should mean *"we have a bug"* — a signal that is worthless if
corrupt uploads also produce 500s. Empty file, non-image bytes, truncated image,
wrong content type, oversized upload and oversized batch each map to a specific
status with an actionable `hint`.

Batch is **partially fault-tolerant**: a well-formed batch returns 200 with
per-item success flags, so one corrupt file does not discard fifteen good
predictions.

### 6.5 Latency is measured end-to-end over HTTP

Not by timing `model.forward()`. Multipart parsing, JPEG decode, preprocessing
and serialisation all sit on the request path and are frequently a larger share
of wall-clock time than the convolutions. Optimising the model while decode
dominates is wasted effort, and only the end-to-end number reveals that.

Percentiles rather than a mean, because latency distributions are right-skewed
and a mean hides exactly the tail an SLA is written against.

## 7. Decisions we deliberately did *not* take

Stating what was rejected, and why, is part of justifying what was chosen.

| considered | rejected because |
| --- | --- |
| Embedding-based drift detection | Fires reliably but is uninterpretable — see §2.2. The feature *pattern* is the diagnostic value. |
| KS as a primary trigger | Sample-size dependent; would reject on differences too small to act on and cause alert fatigue. |
| Higher input resolution (224 px) | ~3× the compute for a task already at 0.997 F1 at 128 px. |
| Unfreezing / longer transfer training | ResNet-18 already converged by epoch 3 and still lost on cost. More training would not change the latency verdict. |
| Baking the model into the Docker image | Promoting a new model would require an image rebuild. Mounting it read-only keeps the image a pure runtime and the model a versioned artifact. |
| `ruff format` in CI | Its only disagreement is wrapping `append(Ctor(...))` in an extra indent level, which reads worse here. `ruff check` remains the gate. |
| Committing the EDA as a notebook | Notebooks accumulate untracked state and diff badly. The EDA is a `# %%`-marked script — cell-runnable in an IDE, convertible via Jupytext, reproducible from the CLI. |

## 8. Known limitations

Judged honestly, the design does not cover the following. Each is a real gap,
not a hypothetical.

**Label bias in accuracy monitoring.** Ground truth is likeliest to arrive for
parts a human already reviewed — i.e. the low-confidence band. Tier-3 accuracy is
therefore measured on a non-random sample and is pessimistic. A production system
would need stratified sampling for labelling.

**No automatic rollback.** A promoted model that degrades needs a human to run
`defectvision package --model <previous>`. Automating it requires canary
deployment with live traffic splitting, beyond this project's scope.

**A single global threshold.** One operating point serves all product variants.
A real line with several SKUs would want per-variant thresholds.

**Cold start on label sufficiency.** A brand-new deployment has no labels, so
Tier-3 rules cannot fire for the first days. Tiers 1 and 2 are the only cover
during that window — which is precisely why they were built.

**Accuracy is high because this dataset is well separated.** Published work on
the same corpus also reports 99%+. The guards against inflated scores are the
near-duplicate grouping (§5.2), the shortcut-leakage check (§5.3), and
validation-only threshold tuning (§4.3) — but the honest statement is that this
task is easier than a typical industrial defect problem, and these numbers should
not be read as transferable to a harder one.
